# photo-ingest Specification

## Purpose

Defines how an original image gets from an administrator's machine into object storage and becomes a listable photo: the two-phase reservation-and-finalize flow, the presigned upload window, the validation and derivative generation that finalization performs, and how incomplete or invalid uploads are kept out of public results.

Error codes below are named as tRPC codes, since that is the transport. `BAD_REQUEST` surfaces as HTTP 400, `UNAUTHORIZED` as 401, and `NOT_FOUND` as 404.

## Requirements

### Requirement: Upload is a two-phase reserve-then-finalize flow

Uploading a photo SHALL take two steps, both performed by the dmbk GraphQL API on the administrator's behalf. First, the administrator reserves an upload, and the API creates a photo record in `pending` state and returns that photo together with a presigned upload target for the original. Second, after the bytes have been placed at that target, the administrator finalizes the upload, and the API validates the stored object and promotes the record to `ready`. Image bytes SHALL be transferred directly to object storage and SHALL NOT pass through this application or the API. A record SHALL only ever hold the states `pending`, `ready`, or `failed`.

#### Scenario: Reservation returns an upload target

- **WHEN** an authenticated administrator reserves an upload, declaring the file's content type and byte size
- **THEN** a `pending` photo record is created, and the reservation returns that photo, including its identifier, and a presigned upload URL; the storage key is chosen by the system and is not supplied by or returned to the client

#### Scenario: Full upload lifecycle

- **WHEN** an administrator reserves an upload, places the image bytes at the presigned URL, and then finalizes that photo
- **THEN** the record becomes `ready` and the photo appears in public listings

#### Scenario: Bytes do not traverse the application

- **WHEN** an administrator uploads an original larger than the application's request body limit
- **THEN** the upload still succeeds, because the bytes go directly to object storage rather than through an application route

#### Scenario: AVIF finalizes

- **WHEN** an administrator uploads and finalizes a valid AVIF original
- **THEN** the record becomes `ready`, with `image/avif` as its recorded content type

### Requirement: Presigned upload URLs are narrow and short-lived

A presigned upload URL SHALL grant write access to exactly one storage key, SHALL expire within 15 minutes of issuance, and SHALL bind the content type declared at reservation. The URL SHALL NOT grant read, list, delete, or overwrite access to any other object. Storage keys SHALL be generated by the system from an unguessable identifier rather than from the client-supplied filename, so that a client cannot choose where its bytes land or collide with an existing object.

#### Scenario: Presigned URL expires

- **WHEN** a client attempts to upload to a presigned URL more than 15 minutes after it was issued
- **THEN** object storage rejects the upload

#### Scenario: Presigned URL is scoped to one key

- **WHEN** a client attempts to use a presigned upload URL to write to a storage key other than the one it was issued for
- **THEN** the write is rejected

#### Scenario: Client filename does not determine the key

- **WHEN** two administrators reserve uploads for files with the identical name
- **THEN** the two reservations receive different storage keys and neither overwrites the other

#### Scenario: Path traversal in the supplied filename

- **WHEN** a reservation declares a filename containing path separators or traversal segments
- **THEN** the generated storage key contains no traversal segments and stays within the photo prefix

### Requirement: Reservation rejects unsupported and oversized files

The system SHALL accept reservations only for JPEG, PNG, WebP, and AVIF content types, and only for a declared byte size at or below 50 MB. A reservation naming any other content type, or declaring a larger size, SHALL be rejected with `BAD_REQUEST` and SHALL NOT create a photo record or issue a presigned URL. The declared content type SHALL be treated as a claim to be re-checked at finalization, never as proof of the file's actual format.

#### Scenario: Unsupported content type is rejected

- **WHEN** an administrator reserves an upload declaring a content type such as `application/pdf` or `image/gif`
- **THEN** the request is rejected with `BAD_REQUEST`, no record is created, and no presigned URL is issued

#### Scenario: Oversized file is rejected at reservation

- **WHEN** an administrator reserves an upload declaring a byte size above 50 MB
- **THEN** the request is rejected with `BAD_REQUEST` and no presigned URL is issued

#### Scenario: Supported type is accepted

- **WHEN** an administrator reserves an upload declaring a JPEG, PNG, WebP, or AVIF content type within the size limit
- **THEN** the reservation succeeds

### Requirement: Finalization verifies the stored object before promoting it

On finalization the system SHALL read the stored original from object storage and confirm that the object exists, that it decodes as an image, that its actual format is one of the supported formats, and that its actual byte size is within the limit. Only when every check passes SHALL the record be promoted to `ready`. If any check fails, the record SHALL be marked `failed` with a reason, SHALL NOT appear in public listings, and the operation SHALL fail with `BAD_REQUEST` naming the failure. The declared content type from reservation SHALL NOT be trusted in place of these checks.

#### Scenario: Finalizing before the bytes are uploaded

- **WHEN** an administrator finalizes a photo whose presigned upload was never completed, so no object exists at its key
- **THEN** the request is rejected with `BAD_REQUEST`, the record does not become `ready`, and the photo does not appear in listings

#### Scenario: Uploaded bytes are not an image

- **WHEN** the object stored at a photo's key does not decode as an image, despite the reservation having declared an image content type
- **THEN** finalization fails with `BAD_REQUEST`, the record is marked `failed`, and the photo does not appear in listings

#### Scenario: Actual format differs from the declared type

- **WHEN** the stored object decodes as an image whose actual format is not among the supported formats, regardless of what content type was declared
- **THEN** finalization fails with `BAD_REQUEST` and the record is marked `failed`

#### Scenario: Valid original is promoted

- **WHEN** the stored object decodes as a supported image within the size limit
- **THEN** the record is promoted to `ready`

### Requirement: Finalization records intrinsic dimensions and generates derivatives

On successful finalization the system SHALL record the original's intrinsic pixel width and height, its actual byte size, and its actual content type on the photo record. It SHALL also generate and store three derivatives: a thumbnail whose longest edge is 400 pixels, a grid variant whose longest edge is 1000 pixels, and a display variant whose longest edge is 1600 pixels. All three derivatives SHALL preserve the original's aspect ratio and SHALL NOT be enlarged beyond the original's own dimensions. Derivative storage keys SHALL be recorded on the photo record. If derivative generation fails, the record SHALL be marked `failed` rather than promoted with missing variants.

#### Scenario: Dimensions are recorded

- **WHEN** a 6000 by 4000 pixel original is finalized
- **THEN** the photo record carries a width of 6000 and a height of 4000

#### Scenario: Derivatives are generated

- **WHEN** a 6000 by 4000 pixel original is finalized
- **THEN** a thumbnail with a longest edge of 400 pixels, a grid variant with a longest edge of 1000 pixels, and a display variant with a longest edge of 1600 pixels are stored, all at the original's 3:2 aspect ratio

#### Scenario: Original smaller than a derivative target

- **WHEN** an original whose longest edge is 900 pixels is finalized
- **THEN** neither the grid variant nor the display variant is enlarged past 900 pixels on its longest edge, and the thumbnail is still produced at 400 pixels

#### Scenario: Portrait orientation

- **WHEN** a 3000 wide by 4500 tall original is finalized
- **THEN** each derivative's longest edge is its height, and all three preserve the 2:3 aspect ratio

#### Scenario: Derivative generation fails

- **WHEN** derivative generation cannot complete for a stored original
- **THEN** the record is marked `failed`, is not listed publicly, and the response reports the failure

### Requirement: Title and keywords may be supplied at either phase

A reservation MAY carry a title and keywords, and a finalization MAY carry a title and keywords. Values supplied at finalization SHALL replace values supplied at reservation. Both phases SHALL apply the same keyword normalization and the same title rules that govern any other photo write. Neither a title nor keywords SHALL be required in order to finalize a photo.

#### Scenario: Metadata supplied at reservation

- **WHEN** an administrator reserves an upload with a title and keywords and then finalizes without supplying any metadata
- **THEN** the finalized photo retains the title and keywords given at reservation

#### Scenario: Metadata replaced at finalization

- **WHEN** an administrator reserves an upload with one title and set of keywords, then finalizes with a different title and set of keywords
- **THEN** the finalized photo carries the values given at finalization

#### Scenario: No metadata supplied

- **WHEN** an administrator reserves and finalizes an upload without a title or keywords
- **THEN** the photo is finalized successfully with no title and no keywords

### Requirement: Incomplete uploads never surface publicly and can be cleaned up

A photo record that is not `ready` SHALL be excluded from every public read — listings, single-photo lookups, and keyword counts alike. A `pending` record whose presigned window has passed without a successful finalization SHALL be treated as abandoned, and the system SHALL provide a means of removing abandoned and `failed` records together with any bytes they left in object storage. Removing an abandoned record SHALL NOT affect any `ready` photo.

#### Scenario: Pending photo is hidden from listings

- **WHEN** a photo record is in `pending` state and a caller requests the public listing
- **THEN** that photo is absent from the results and is not counted toward any keyword's usage count

#### Scenario: Pending photo is hidden from direct lookup

- **WHEN** a caller requests a single photo by the identifier of a `pending` or `failed` record
- **THEN** the request is rejected with `NOT_FOUND`

#### Scenario: Abandoned upload is cleaned up

- **WHEN** cleanup runs against a `pending` record whose upload window expired without finalization
- **THEN** that record is removed along with any bytes stored under its keys, and no `ready` photo is altered

### Requirement: A batch is bounded and its uploads are independent

Several photos MAY be ingested together as a batch. A batch SHALL carry at most 10 files; a larger one SHALL be refused before any reservation is made, so no partial batch is created and abandoned.

Batching SHALL NOT change the ingest contract for any individual photo: each file is reserved, uploaded, and finalized exactly as a lone photo is, and the server SHALL NOT need to know that a batch exists. Consequently each file's outcome SHALL be independent — one file's failure neither prevents another from finalizing nor undoes one already finalized.

#### Scenario: A batch at the limit

- **WHEN** ten files are ingested together
- **THEN** each is reserved, uploaded, and finalized, and all ten become listable

#### Scenario: Over the limit

- **WHEN** more than ten files are submitted together
- **THEN** the batch is refused before any reservation is made, and no photo record exists for any of them

#### Scenario: One file fails to finalize

- **WHEN** one file in a batch is rejected at finalization because its bytes do not decode as an image
- **THEN** that photo is marked failed and every other file in the batch still finalizes normally

#### Scenario: A failure does not undo a success

- **WHEN** a file fails after another in the same batch has already finalized
- **THEN** the finalized photo remains `ready`, with its derivatives and keyword counts intact

#### Scenario: Each file is validated on its own bytes

- **WHEN** a batch contains files of different formats and sizes
- **THEN** each is validated against its own decoded bytes, not against any other file in the batch

### Requirement: Keywords may be shared across a batch

The same keywords MAY be applied to every photo in a batch. Shared keywords SHALL be normalized once and applied identically to each photo, so a batch cannot produce inconsistent tagging across photos submitted together. Keyword counts SHALL reflect only the photos that actually became visible, so a file that failed contributes nothing.

#### Scenario: Shared keywords are applied to every photo

- **WHEN** a batch of four files is ingested with the keywords `film` and `harbor`
- **THEN** all four photos carry both keywords

#### Scenario: Shared keywords are normalized once

- **WHEN** a batch is ingested with the keyword `Black and White`
- **THEN** every photo in it carries the slug `black-and-white`, identically

#### Scenario: A failed file contributes no keywords

- **WHEN** one file in a batch of three fails and the other two finalize
- **THEN** the keyword counts reflect two photos, not three

### Requirement: A photo finalized before the grid variant existed can be brought up to date

A photo whose record predates the grid variant SHALL remain `ready`, readable, and listed, with its existing derivatives intact. The system SHALL provide a maintenance operation that generates the missing grid variant for such photos from their stored originals and records its key, without re-uploading the original, without changing the photo's identifier, title, keywords, dimensions, visibility, or creation time, and without disturbing photos that already have one.

The operation SHALL be able to report what it would do without doing it. A photo whose grid variant cannot be generated SHALL be reported and left exactly as it was — still `ready`, with its other derivatives untouched — rather than being marked `failed`.

#### Scenario: A pre-existing photo gains the variant

- **WHEN** the maintenance operation runs against a `ready` photo that has no grid variant
- **THEN** a grid variant is generated from that photo's stored original, its key is recorded on the record, and the photo's title, keywords, dimensions, visibility, and creation time are unchanged

#### Scenario: Photos that already have one are left alone

- **WHEN** the operation runs against a photo that already has a grid variant
- **THEN** that photo is skipped and its stored objects are not rewritten

#### Scenario: The operation can be rehearsed

- **WHEN** the operation is run in a mode that reports without acting
- **THEN** it names the photos that would be processed and writes nothing to storage or to any record

#### Scenario: One photo cannot be processed

- **WHEN** the original for one photo cannot be read or cannot be decoded
- **THEN** that photo is reported, is left `ready` with its existing derivatives intact, and the remaining photos are still processed

#### Scenario: A photo without the variant is still usable

- **WHEN** a `ready` photo has no grid variant and the maintenance operation has not yet run
- **THEN** the photo is listed and readable, and its remaining variants are exposed as they were before
